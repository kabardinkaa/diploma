# Эксперимент с мультиагентной системой

## Постановка задачи

Эксперимент сравнивает две реализации ответа по корпоративной базе знаний:

- single-agent самостоятельно вызывает RAG и формирует ответ;
- multi-agent использует LangGraph Supervisor для последовательной работы
  researcher и writer.

Обе реализации заново отвечали на одинаковые пять вопросов одной локальной
моделью `qwen/qwen3.6-35b-a3b` через LM Studio. Thinking был отключён, прогоны
выполнялись строго последовательно. Embedding-модель
`intfloat/multilingual-e5-base` загружалась из локального cache, а существующая
коллекция Qdrant `corporate_rag` использовалась только для чтения.

## Реализации

Single-agent построен через `langchain.agents.create_agent` и имеет один
`search_knowledge_base` tool.

Multi-agent построен через `langgraph_supervisor.create_supervisor`:

- supervisor выбирает следующий этап;
- researcher имеет RAG tool, выполняет поиск и возвращает факты с источниками;
- writer работает с `tools=[]` и формирует финальный ответ;
- роли используют shared message state и `output_mode="last_message"`;
- состояние каждого запуска хранится в `InMemorySaver` с отдельным `thread_id`;
- штатный маршрут имеет handoff budget 2: researcher, затем writer;
- если после успешного researcher supervisor ошибочно завершает работу,
  deterministic post-model fallback передаёт управление writer;
- после writer граф переходит в deterministic final node без дополнительного
  LLM-синтеза supervisor.

Researcher повторно обращается к RAG только после пустого первого результата.
Во всех пяти финальных multi-agent прогонах был ровно один retrieval и не более
трёх уникальных источников.

## Методика

Agent и quality judge использовали один локальный endpoint
`http://127.0.0.1:1235/v1`. Quality измерялся RAGAS Faithfulness через локальный
LLM-as-judge с той же моделью. Для ответа без найденных контекстов evaluator
возвращает `0.0`, поэтому out-of-scope результат нужно читать вместе с фактом
отсутствия retrieval, а не как штраф за выдуманные технические сведения.

Сырые данные находятся в `experiments/results.json`. Все значения получены в
финальном benchmark 5 x 2; smoke-результаты в таблицы не включались.

## Сравнение

| Метрика | Single-agent | Multi-agent | Δ |
|---|---:|---:|---:|
| Токены на запрос | 1759.40 | 3214.80 | +1455.40 (+82.72%) |
| LLM-вызовов на запрос | 2.20 | 4.60 | +2.40 (+109.09%) |
| Latency p50, мс | 13748.16 | 34322.72 | +20574.56 (+149.65%) |
| Передач управления на запрос | 0.00 | 2.00 | +2.00 |
| Качество ответа | 0.7909 | 0.7490 | -0.0419 (-5.30%) |

Token multiplier multi-agent к single-agent равен **1.83x**. Multi-agent не дал
прироста качества: средний Faithfulness снизился на 0.0419, при этом среднее
число токенов выросло на 82.72%. Медианная задержка выросла на 149.65%, а число
наблюдаемых LLM-вызовов более чем удвоилось. Для последовательного ответа по
общему RAG-контексту такая цена не оправдана.

## Сравнение с Anthropic

Ориентир Anthropic около **15x токенов** и **+90.2% качества** относится к их
breadth-first research кейсу, где несколько агентов параллельно исследуют разные
ветви большой задачи. Наш фактический множитель равен 1.83x, но при этом качество
не выросло, а снизилось на 5.30%.

Корпоративная поддержка в этом эксперименте использует один общий RAG-корпус и
линейный процесс `research -> write`. Здесь нет широкого пространства независимых
исследовательских ветвей, ради которого дополнительные агенты могут окупиться.
Поэтому результаты breadth-first research нельзя напрямую переносить на этот
сценарий: различаются задача, стратегия поиска, степень параллелизма и критерий
качества.

## Решение

**НЕ ИСПОЛЬЗОВАТЬ multi-agent в production-части диплома.**

Финальная production-рекомендация: оставить single-agent с tools. Он показал
более высокое среднее качество `0.7909` против `0.7490`, использовал на 45.3%
меньше токенов относительно multi-agent и имел существенно меньшую p50 latency.
Последовательное разделение researcher и writer добавляет координационные вызовы,
но не расширяет доступный RAG-контекст и не создаёт полезного breadth-first
исследования. Supervisor остаётся учебным экспериментом в `experiments/` и не
переносится в `app/agents/`.
